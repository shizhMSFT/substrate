# Agent Substrate 路线图

## 概述

Agent Substrate 是一个基于 Kubernetes 的系统，用于构建基于独立、有状态容器实例的多租户应用。Substrate 建立在可沙箱化、可快照的 Pod 之上，增加了在不调用 Kubernetes 调度器的情况下更新 Pod 中运行容器的能力。Substrate 使这些容器能够在活跃与非活跃生命周期阶段之间快速切换，从廉价的云对象存储中的快照进行快速挂起和恢复，而不会丢失内存或文件系统状态。这对于智能体（agentic）工作负载尤其关键，因为它们经常在活跃（处理用户输入）和空闲（等待 LLM 或工具调用完成）之间来回震荡。有了 Substrate，可以在这些空闲时刻回收资源，供其他工作负载使用。这既实现了比单独使用 Pod 更高的效率，又实现了更大的规模，同时仍然利用 Kubernetes 来配置容量、配置网络和存储，并管理 Substrate 自身。

本项目正努力快速推进，以找到适合不断变化的智能体工作负载市场的正确能力集合。以下是我们的优先事项。任何与这些优先事项不一致的工作都可能应当被推迟。

1. 确定影响其余各项优先事项的架构决策。
2. 唤醒（wakeup）的性能与可靠性，包括挂起/恢复以及快照管理。
3. 一个快速、可扩展的控制平面，包括存储层、可靠性和安全性。
4. 有用的身份（identity），使得策略可以基于身份来编写。
5. 有用的策略（policy），包括用户如何指定入站（ingress）、出站（egress）和对等（peer）网络。
6. 运行时模块化，使得可以使用不同种类的沙箱（gVisor、microVM 等）。

下面是一组更细粒度的工作，我们认为它们与上述优先事项一致。

## 即将推出：高优先级

### Actor 管理（计算）

* 通过 ActorTemplate（或新的 ActorDeployment API）实现 actor 版本控制，支持 A/B 测试和滚动发布策略。
* 命名空间或类似概念，用于将相关 actor 分组，既便于管理，也便于编写 actor 间授权策略。
* Actor 分叉/克隆（Forking/Cloning）：能够从现有检查点（'State Root'）分支出一个新的逻辑 actor，以支持复杂的智能体推理路径。
* Worker 水平自动扩缩：能够快速扩容节点并预热 Pod 以满足 actor 需求。
* 阐明 actor 生命周期，包括哪些数据会在哪些事件间保留（例如 gvisor 升级 \-\> 内存快照丢失）
* 决定：我们支持哪些 actor 运行模式？我们能否对其进行优先级排序和分阶段实施？假设我们始终持久化"工作"数据
  * 每次激活都从 OCI 全新启动
  * 每次激活都从黄金（golden）快照恢复
  * 持久化 rootfs（在可能时），每次激活都从干净的二进制启动
  * 持久化 rootfs 和内存（在可能时），完整进程恢复

### Worker 管理

* Worker 类别（例如：廉价硬件上的免费层，优质硬件上的高级层）
* 可互换的 worker 池（某个类别中的任何 worker 都可以运行该类别中的任何 actor）

### 控制平面

* 用户授权
* 优秀的 CLI

### 网络

* Actor 安全边界实现，默认拒绝，配合大规模、低延迟的显式 ACL。这与部分安全项有重叠（见下文）。
* 策略定义：框架（外部）与 Actor 之间、Actor 之间、Actor 出站（Egress）。
* 标准化 DNS 网格（Mesh）：迁移到生产级路由格式（\<id\>.actors.resources.substrate.ate.dev），以实现位置透明的 actor 间通信。

### 存储

* 决定：Redis/ValKey 是 API 存储的正确答案吗？
* gVisor 快照/恢复优化
  * 存储分层（本地 zswap、本地 SSD、点对点、blob）
  * 增量快照
* 支持 S3（通过插件）
* "rootfs"和内存快照与"工作"空间的不同生命周期。需要相应的 API 界面来指定挂载位置。
* ConfigMap 作为卷（volume）
* 调度中的数据局部性（需要通过 API 暴露每个节点上可用的快照）

### 安全

* 目标是在共享同一 Kubernetes 节点的互不信任 actor 之间建立两道安全边界。
* 所有系统组件之间安全的 mTLS 认证和授权。
* 安全的 actor 间认证和授权策略，可随 actor 生命周期在带内（in-band）部署，保持低延迟部署。
* 能够为单个 actor 指定网络策略，包括 L7 协议感知的过滤规则，可随 actor 生命周期在带内部署，保持低延迟部署。
* 凭据注入，包括 actor 身份，通过代理进行，以消除向 actor 暴露加密密钥和 bearer token。
* 对 API 和生命周期操作进行审计日志记录。
* 用于威胁检测遥测的沙箱集成。
* 加固 actor 网络，使其进一步与周围节点隔离（例如借助当前网络

### 可观测性

* 会话感知遥测关联：自动化 OTLP 导出，所有日志、指标和追踪都原生地打上 Substrate Actor ID 和 worker ID 标签。
* Prometheus 指标

### 性能与可靠性

* 有代表性的工作负载/流量模式
* 预置负载测试和基准测试的计算/基础设施
* 基准测试结果的存储与可视化
* 将调试集成到负载测试中
* 状态存储扩展：水平分片支持（通过 Redis Hash Tags），以实现管理 100 万以上并发 actor。
* 仅磁盘恢复策略：支持成本优化的休眠，仅保留文件系统状态，跳过 RAM 恢复，适用于无状态或能"冷"启动的智能体。

### 测试

* 支持在 KinD 集群上进行本地开发和测试。
* 定义充分的测试矩阵（应测试哪种容器系统、云、其他配置项）
* 老化（burn-in）测试，以检测内存/其他资源泄漏
* 模拟 LLM/其他依赖项

### 集成

* 与 Agent Executor 紧密集成，以在 Kubernetes 上部署 AX。
* Agent Development Kit (ADK) 原生支持：为 ADK 开发一流的绑定，让开发者能够构建原生利用 Substrate 生命周期管理和持久工作内存的有状态智能体。
* LangChain 远程执行提供程序：为 LangChain 提供专用的 provider，在持久、沙箱化的环境中运行复杂、长时间运行的智能体工具。
* 原生 MCP 服务器托管：内置支持将 Model Context Protocol (MCP) 服务器作为受管的 Substrate Actor 部署，为任何 LLM 创建一个安全的工具生态系统。
* Actor 间（A2A）调用模型：标准化协议，使 actor 能够通过网关在网格内发现和调用其他 actor。
* 原生 MCP 工具托管：能够将标准 Model Context Protocol (MCP) 服务器定义并部署为受管的 Substrate Actor，为智能体工具提供即插即用的生态系统。

### 可运维性

* 控制平面升级
* Worker 升级
* Gvisor 升级
* API schema 变更
* 从小规模到大规模的增长规划（尤其是关于 CP 分片）

## 我们正在考虑的其他想法

### Actor 管理（计算）

* Worker 垂直自动扩缩和 IPPU（例如，保留上一个快照的内存/CPU 配置，并在分配 actor 时更新 worker pod）
* Actor \-\> worker 选择器（selector）、污点（taint）等。
* 自动化垃圾回收：基于可配置的 TTL 对空闲 actor 进行后台清理

### 存储

* 驱动旧快照保留的策略，以及执行自动清理的控制器
* 点对点的 OCI 和快照共享
* 除 ConfigMap 之外的 K8s"投影"（projected）卷
* 由外部存储插件支持的存储模型（通过 CSI 驱动？）。
* actor 间共享的可写存储（例如 NFS 卷）。

### 安全

* actor 能够将降权后的权限委托给子 actor 和对等 actor。
* 镜像拉取凭据

### 性能与可靠性

* 共享镜像缓存

### 集成

* 有状态编码适配器：为 Claude Code 和 CodeX 提供标准化环境模板，以支持在终端会话间维持持久文件系统状态的 AI 编码任务。

### 管理

* 能够在单个集群中运行多个 substrate
